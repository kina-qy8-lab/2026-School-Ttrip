# 修学旅行 プログラム選択アプリ（v1）

Firebase (Authentication + Firestore) を使った、修学旅行プログラムの申し込み・抽選 Web アプリです。
サーバ不要のフロントエンドのみ（静的ホスティング）で動作します。

---

## 0. まず結論：デプロイは GitHub Pages を推奨します

「GitHub だと個人情報が心配」という懸念は、このアーキテクチャでは**当たりません**。理由：

- このアプリは **静的ファイル（HTML/JS）だけ** を GitHub に置きます。**個人情報（氏名・組・番・メール・申込・抽選結果）は一切 GitHub に入りません**。すべて Firestore に入ります。
- Firebase の `apiKey` などの config はコードに**書いてよい公開情報**です（秘密鍵ではなく「プロジェクト識別子」）。セキュリティは **Firestore セキュリティルール + Authentication** で担保します。
- つまり「コードが公開されること」と「データの安全性」は別問題です。データの安全は `firestore.rules` が守ります。

→ **速度優先で GitHub Pages、データ保護は Firestore ルールで担保**、が無料かつ安全な構成です。
（GAS+HTML は配信が遅く、今回メリットがありません。）

唯一の注意：**生徒名簿 CSV などを GitHub リポジトリにコミットしないこと**。名簿は管理画面から Firestore に登録します（リポジトリには入れない）。

## 1. 無料枠（Spark プラン）で 320 名を運用するための設計

| 項目 | 無料枠の制限 | 本アプリの設計 |
|---|---|---|
| Firestore 読み取り | 50,000/日 | リアルタイム購読は使わず**1回取得＋手動更新**。申込人数は `getCountFromServer`（集計クエリ＝1クエリ1読み取り相当）でカウント |
| Firestore 書き込み | 20,000/日 | 生徒の申込は1人1ドキュメント上書き。抽選はバッチ書き込み |
| Cloud Functions | **Spark では使用不可** | 抽選処理は**管理者ブラウザ上で実行**（クライアントサイド）。サーバ関数は不要 |
| Cloud Storage | 現在 Blaze 必須 | **画像は Storage を使わない**。プログラム画像は URL 指定（リポジトリ内 `images/` か外部URL）で運用 |

320名 × 1日数回アクセス × 1回あたり十数読み取り ≒ 数千〜2万読み取り/日 で、無料枠（5万）に収まる想定です。
混雑（締切直前のアクセス集中）に備え、画面は手動更新ボタン方式にしています。

## 2. データモデル（Firestore コレクション）

```
admins/{email}      ... 既存。{ email, name, active:true }   ← 管理者（教員）の許可リスト
students/{email}    ... 生徒の許可リスト兼名簿。{ email, name, class:"A", number:12 }
programs/{autoId}   ... { name, description, capacity, imageUrl, order, tags }
config/lottery      ... 抽選の日時・進行状態（下記）
applications/{email}... 生徒の現在の申込。{ studentEmail, programId, round, updatedAt }
results/{email}     ... 本番の抽選結果。{ status:"confirmed"|"lost", programId, round, updatedAt }
testResults/{email} ... テストモードの抽選結果（教員練習用・本番には無関係）。形式は results と同じ
```

- **ログインID = Google メールアドレス**。`students` / `admins` の **ドキュメントID は Google が返すメール（小文字）** にしてください。
- 生徒が読めるのは「自分の `students` / `testResults`」「`programs` / `config`」に加えて、**`applications` / `results` は生徒全員が全件を読めます**（書き込みは自分の分のみ）。これは「プログラムごとの申込人数」「残り枠」を表示するために、生徒がプログラム単位で全員分を集計取得する必要があるためです。裏を返すと、生徒同士で「誰がどのプログラムに申込み／確定しているか」はドキュメントIDを知っていれば読める状態になります（修学旅行のプログラム振り分けという性質上、実害は小さい想定ですが、より厳格にしたい場合はプログラムごとの集計専用ドキュメントを別途用意する設計に変更できます）。
- **`class:"99", number:"99"` で登録したアカウントは「教員のテストアカウント」として扱われます**。本番の抽選対象（`results`・定員消費）からは自動的に除外され、テストモードの対象になります。

### config/lottery のフィールド
```json
{
  "round1At":  "<Timestamp 第一次抽選 締切>",
  "round2Enabled": true,
  "round2At":  "<Timestamp 第二次抽選 締切 / round2Enabled=false なら null>",
  "finalAt":   "<Timestamp 最終抽選 締切>",
  "currentRound": "round1",          // round1 | round2 | final
  "round1Done": false,
  "round2Done": false,
  "finalDone":  false,
  "appSnapshot_round1": { "taro@example.ed.jp": "programId..." }  // 各回の抽選実行時、その回の申込内容を自動保存（取り消し用）
}
```
`currentRound` は「いま申し込みを受け付けている回」。管理者が抽選を実行すると次の回へ進みます。
`appSnapshot_<round>` は取り消し機能専用の内部データで、生徒・管理者ともに通常は意識する必要はありません。

## 3. 抽選ロジック（仕様どおり）

管理者画面の「抽選を実行」で、ブラウザ内で計算しバッチ書き込みします。

- **第一次抽選**：申込のある生徒が対象。定員に達していないプログラムは抽選なしで**全員当選**。定員超過のプログラムだけ、定員までランダム抽選。外れた生徒は `lost`。
- **第二次抽選（任意）**：**空き枠の分だけ**抽選。定員に達したプログラムは募集終了（申込不可）。一次で外れた生徒が再申込→抽選。
- **最終抽選**：申込のある生徒を**優先**して空き枠へ抽選。最後に、外れた生徒＋一度も申し込んでいない生徒を、**ランダムに空き枠へ振り分け**。

> 注意：全プログラム定員合計 ≧ 生徒数（320）でないと、最終で配置できない生徒が出ます。管理画面に合計定員チェックを表示します。

### 結果の取り消し（1つ前の回までのみ）

管理画面「抽選」タブの各回に **「結果を取り消す」** ボタンがあります。押せる条件は「**直近に実行した回**」のみです。

- 例：第一次抽選を実行直後 → 「第一次抽選の結果を取り消す」が押せる。取り消すと、その回で確定・落選した生徒は**抽選前（申込み受付中）の状態**に戻り、**抽選直前に選んでいたプログラムの選択内容はそのまま保持**されます（選び直す必要はありません）。
- 例：第一次抽選 → 最終抽選まで進んだ場合 → 押せるのは「最終抽選の取り消し」のみ。第一次抽選には戻れません（次の回の抽選を実行した時点で、それより前の回は取り消せなくなります）。
- 例：第二次抽選を実施しない設定の場合 → 第一次抽選の次は最終抽選なので、最終抽選実行直後は「最終抽選の取り消し」を押すと、第一次抽選の直後（＝最終抽選の受付開始前）の状態に戻ります。

取り消しは「結果（`results`）を削除し、抽選直前に保存しておいた申込内容（スナップショット）を `applications` に書き戻す」という処理です。スナップショットは抽選実行時に自動保存されるため、取り消し操作によってデータが失われることはありません。ただし、**取り消し後に次の回の抽選を実行すると、再び取り消せなくなる**点に注意してください。

### テストモード（教員だけで練習抽選）

管理画面「抽選」タブに **本番モード／テストモード** の切り替えボタンがあります（デフォルトは本番モード）。

- **本番モード**（既定）：組=99・番=99 で登録した教員アカウントを**除外**し、生徒のみを対象に、プログラムの実際の定員で抽選します。
- **テストモード**：組=99・番=99 で登録した教員アカウントの**うち、現在受付中の回に申込み済みの人だけ**を対象に、**各プログラム定員1名固定**で抽選します。「落選したらどう見えるか」をすぐ確認できるよう、あえて定員を絞っています。

テストモードの抽選結果は、生徒データや本番の定員・抽選進行状況（`round1Done` 等）に**一切書き込みません**（専用の `testResults` コレクションに保存）。そのため、

- 本番の抽選実行・取り消しには一切影響しません。
- 「テスト結果をリセット」ボタンで何度でもやり直せます。
- 教員アカウントで管理画面右上の「生徒画面」に切り替えると、テストモードの抽選結果（確定の搭乗券 or 落選画面）がそのまま表示され、**生徒が実際に見る画面と同じ体験**を確認できます（画面には「🧪 テストモードの結果です」と明記されます）。
- Excel名簿出力（クラス毎・プログラム毎）には教員テストアカウントは含まれません。

使い方の流れの例：教員アカウント（組99・番99）で生徒画面からプログラムに申込み → 管理画面で「テストモード」に切り替えて「テスト抽選を実行」→ 教員アカウントで生徒画面に戻り、当選・落選それぞれの見え方を確認 → 問題なければテスト結果をリセットし、本番モードで実際の抽選を実行。

## 4. セットアップ手順

> **ファイルは `index.html` 1枚に統合しました。**`admin.html` はもう不要です（管理画面は `index.html` 右上の「🔑 管理者」ボタンから開きます）。

1. `firebase-config.js` を自分のプロジェクトの値に書き換える（Firebase コンソール → プロジェクト設定 → ウェブアプリ）。
2. Authentication で **Google ログインを有効化**（済みとのこと）。
3. Firestore のルールを `firestore.rules` の内容に置き換えて公開。
4. リポジトリを GitHub にプッシュ → Settings → Pages → ブランチを `main` /（root）で公開。
5. 公開URL（`https://ユーザー名.github.io/リポジトリ名/`）を開く＝**生徒画面**。
6. 教員は右上の **「🔑 管理者」ボタン** → 教員 Google アカウントでログイン → 管理ダッシュボード。
   - 「添付PDFの8件を投入」で初期プログラム登録（任意・1回だけ）。
   - 「生徒名簿」タブで CSV を貼り付けて一括登録。
   - 「抽選」タブで日時を設定・実行。
   - 管理画面の右上「生徒画面」リンクで生徒ビューに戻れます。

### 生徒名簿 CSV 形式（ヘッダ必須）
```
email,name,class,number
taro@example.ed.jp,山田太郎,A,1
hanako@example.ed.jp,佐藤花子,A,2
```

## 5. プログラム画像の追加方法

管理画面 → 「プログラム」タブ → 各プログラムの「編集」（新規追加でも可）を開くと、**「画像URL」欄**があります。ここに画像のURLを入力すると、生徒側のチケット・管理画面のカード一覧の両方に反映されます（入力するとその場でプレビュー表示されます）。空欄のままならカラーバンドのみのシンプルな表示になります。

入力できるURLは2パターンです。

1. **外部URL（一番手軽）**：すでにインターネット上にある画像のURLをそのまま貼り付けます。例：`https://example.com/photos/program1.jpg`。手元の写真をすぐ使いたい場合は、Google フォトの「リンクを共有」やimgur等の画像ホスティングサービスにアップロードしてURLを取得するのが簡単です。
2. **リポジトリ内の画像（管理しやすい）**：GitHubリポジトリの `images/` フォルダに写真ファイルをアップロードし、`images/01.jpg` のような**相対パス**を画像URL欄に入力します。手順は次のとおりです。
   - GitHub上でリポジトリを開き、`images/` フォルダに入る（なければ作成）。
   - 「Add file」→「Upload files」で写真をドラッグ＆ドロップしてコミット。
   - 管理画面の画像URL欄に `images/ファイル名.jpg` と入力して保存。

どちらの方法でもFirebase Storageは使わない（無料枠維持のため）ので、課金は発生しません。画像サイズの目安は横800px・容量300KB程度に収めると表示が軽くなります。

## 7. 管理者が生徒画面を確認したいとき

教員アカウントを `students` にも登録しておくと（組・番は実在しない値、例：組=99、番号=99 など、運用上わかりやすい値でOK）、管理画面の右上に **「生徒画面」リンク** が表示され、クリックすると生徒側の画面（チケット選択・抽選結果）にそのまま切り替わります。生徒画面の右上には「🔑 管理者」ボタンが出るので、管理画面にいつでも戻れます。

生徒登録がない管理者アカウントでは「生徒画面」リンク自体が表示されません（=押しても何も起きない、という分かりにくい挙動にはなりません）。

## 8. よくあるつまずき

- **「管理者権限がありません」と出る**：原因はほぼ以下のどれかです。今回は管理画面のエラー表示が**具体的な理由を出す**ようにしたので、それも見てください。
  1. **ドキュメントIDがログイン中メールと一致していない**。`admins` コレクションの**ドキュメントID自体**が、Google でログインしたメールアドレス（小文字）と完全一致している必要があります。よくある失敗：ドキュメントIDが自動生成IDになっていて、メールを `email` フィールドにだけ入れている／大文字小文字・前後の空白・別アドレスでログインしている。
  2. **`active` が真偽値の `true` でない**。文字列の `"true"` ではダメです。Firestore で型が「boolean」「true」になっているか確認。
  3. **ルール未反映**。`firestore.rules` を公開（デプロイ）し忘れ。
  ※ セキュリティルールは `request.auth.token.email`（＝Googleアカウントのメール）をそのままドキュメントIDとして照合します。Google のメールは通常すべて小文字なので、**ドキュメントIDは小文字のメール**にしてください。
- **「The query requires an index」エラー**：申込人数カウントは `programId` と `round`（または `status`）の複合クエリを使うため、初回に Firestore が複合インデックスの自動作成リンクを出します。`applications` 用と `results` 用、両方の複合インデックス作成を促されることがあります。リンクを1回クリックして作成すれば解決します（数分で有効化）。
- **第一次抽選後、生徒画面でプログラムの募集人数が全部「0」や満員のように見える**：2つの原因が重なっていたため両方を修正しました。(1) 生徒側の表示が「今回のラウンドで新たに申し込んだ人数」しか見ておらず、前の回で確定済みの人数を考慮していなかった → 確定人数（`results`）を踏まえた「空き枠」表示に修正。(2) 従来の `firestore.rules` では `applications` / `results` の読み取りが「自分のドキュメントのみ」に制限されており、プログラム単位の集計クエリ自体が権限エラーになり得た → 生徒全員が読めるようルールを修正（本READMEの最新の `firestore.rules` を再度 Firebase コンソールに反映してください）。**この修正を反映するには、コード（index.html）の更新に加えて、`firestore.rules` を Firebase コンソールで必ず再公開してください。**
- **ログインできる Google アカウントの種類**：学校配布アカウント（Google Workspace for Education など）を想定。Authentication の「承認済みドメイン」に `*.github.io` または独自ドメインを追加してください。
- **画像が表示されない**：`imageUrl` は空欄でOK（カラーバンドで表示）。指定する場合は `images/xxx.jpg`（リポジトリ内）か `https://...` の完全URL。Storage は使いません（無料維持のため）。
- **抽選は取り消せません**：実行前に必ず「抽選」タブの申込状況テーブルを確認してください。テスト用 Firebase プロジェクトで通し試験してから本番投入を推奨します。
